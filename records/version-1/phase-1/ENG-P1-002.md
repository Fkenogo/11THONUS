## 3. Purpose

`ENG-P1-002` built the shared `authenticate → validate → log → respond` command foundation every later domain service depends on: command and event contracts, a shared error model, correlation-ID propagation, structured operational logging, a Firestore-backed idempotency service, an event outbox with retry and dead-letter handling, and the `dispatchCommand` orchestrator tying them together — per the [Engineering Implementation Programme](../../../docs/05-implementation/change-tracking/engineering-implementation-programme.md), Phase 1 table, and TRD22 §22.11's own Phase 1 exit criterion ("shared server command can authenticate, validate, log and return a standard response").

## 15. Risks and Non-Blocking Observations

Carried forward from the Technical Review (§11) and the Merge Verification Report, not re-litigated here:

1. Failed idempotency records are currently retryable (a disclosed interpretation choice, TRD11 §11.14 does not address this case explicitly).
2. Idempotency `"processing"` records have no expiry or abandoned-reservation recovery (unlike the outbox's `claimedAt` mechanism).
3. Outbox claim timeout (`CLAIM_TIMEOUT_MS = 5 * 60_000`) is a provisional, disclosed numeric choice, not TRD-specified.
4. Retry/backoff constants (`MAX_RETRIES = 5`, `INITIAL_BACKOFF_MS = 1_000`, `BACKOFF_MULTIPLIER = 2`) are the same category of provisional choice.
5. No domain consumer yet exists to validate the foundation against real business logic — expected at this stage, per TRD22 §22.11's own Phase 1 exit criterion.
6. **CI-timing observation (accepted as an environmental risk, not a code defect):** CI on the Technical Review's final commit failed twice — on two different, seemingly unrelated tests, one an original pre-`CR1` test with no prior failure history — before passing cleanly on a third attempt with no code change. Targeted investigation (70+ adversarial concurrent-pair stress-test calls against the exact `checkAndReserveIdempotencyKey` mechanism, run directly against a real Firestore Emulator instance, both sequential and truly-parallel) found zero reproducible defects, alongside directly-measured, highly variable multi-second Firestore-emulator transaction-retry latency. This pointed toward Firebase Emulator/CI-runner timing sensitivity rather than a deterministic code defect. The Founder reviewed this exact finding (Technical Review §7.1) and authorized merging PR #12 without requesting further investigation or correction — that authorization is the evidence supporting this item's acceptance as a documented, accepted residual risk rather than an unresolved defect.

## 17. Lessons Learned

- A design believed to avoid a schema change (using Firestore's own `updateTime` document metadata as an outbox ownership token) was empirically disproven by its own failing real-emulator tests during `CR1` — Firestore does not advance `updateTime` on a same-value write, which is exactly what a reclaim of an already-`"processing"` entry does. The corrected design (`OutboxEntry.claimedAt`, a genuine, minimal, Founder-authorized field addition) held up under subsequent heavy concurrent-load stress testing (70+ pair-attempts, zero defects) — a concrete instance of TDD against a real dependency catching a defect that unit tests and initial design reasoning both missed.
