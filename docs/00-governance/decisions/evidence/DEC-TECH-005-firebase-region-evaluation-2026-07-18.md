# DEC-TECH-005 Evidence Pack — Firebase/GCP Region Evaluation

> ⚠️ **This evidence pack is advisory, not a final region selection.** No region has been selected. Candidates are shortlisted only where [Part A's legal evidence pack](DEC-LEGAL-006-cross-border-hosting-evidence-2026-07-18.md) found them at least "potentially admissible with safeguards" — none was found unconditionally admissible, so **every candidate below still requires the legal confirmations listed in Part A §7 before any selection is final.** Full citations are in the companion [Source Register](DEC-LEGAL-006-DEC-TECH-005-source-register-2026-07-18.md).

## 0. Jurisdiction and Legal-Admissibility Gate

Per Part A §8 (corrected 2026-07-18 following direct review of Burundi's primary statutory text), no jurisdiction category was found unconditionally admissible; every candidate below is carried forward as **potentially admissible pending confirmation** of (a) the contents of Burundi's Ministerial adequacy list and the operational status of its new data protection Agency for approving alternative safeguards, and (b) the practical mechanics of Rwanda's Article 48/50 NCSA-authorization pathway. No candidate is excluded outright on the evidence gathered so far, but none should be treated as legally cleared either.

**Key finding, applies to every candidate equally — narrowed further (2026-07-18, second correction pass):** Firebase's own documentation lists which products *require* a location setting (Firestore, Realtime Database, Cloud Storage, Cloud Functions, Firebase AI Logic, Analytics, App Hosting, SQL Connect) — **Authentication is not among them** [T6]. The controlled statement this evidence pack uses is: **Firebase Authentication does not expose a project-level location-selection control comparable to Firestore or Cloud Storage.** That is as far as the directly-reviewed official documentation goes. **Explicit limitation:** the official documentation reviewed for this evidence pack does not itself establish the precise residency of all Firebase Authentication data (where user records, session tokens, and related metadata are actually stored or processed) — the absence of a *location-selection control* is not the same claim as data being globally distributed, globally accessible, or definitively outside any particular jurisdiction, and this pack does not assert any of those stronger claims. **Confirmation of Authentication's actual data-residency position must be obtained from Google's applicable service terms, data-processing documentation (e.g. Firebase's Data Processing and Security Terms), or direct provider clarification before this fact is relied upon for legal approval.** Regionalized Firebase Auth has been publicly discussed as a future roadmap item, but **no source reviewed in this pass confirms it has reached general availability as of mid-2026** [T8] — cited only for roadmap color, not as authority for Authentication's current residency position.

**Key finding, `africa-south1`-specific — corrected and split into two separate services (2026-07-18, second correction pass):** Cloud Scheduler and Cloud Tasks are both **not** available in `africa-south1` [T4, T14]. **These are two distinct services with two distinct evidentiary positions — they should not be treated as one problem with one fix.**

- **Cloud Scheduler has a documented or strongly supported cross-region HTTP-target pattern.** Cloud Scheduler's own architecture does not require a job to run in the same region as its HTTP target — a Scheduler job created in any supported region (e.g. `europe-west1`) can invoke an HTTPS endpoint (such as a Cloud Function) running in `africa-south1`, using OIDC/OAuth authentication [T17]. This means a manually-configured cross-region pattern is technically viable and is **not merely "a small workaround"** — it is a specific architecture requiring deliberate implementation, not something Firebase's tooling does automatically. **A material caveat:** Firebase's own automatic tooling for 2nd-generation scheduled functions (`onSchedule`) provisions its underlying Cloud Scheduler job in the **same region as the function by default**, and does not reliably block or redirect deployment when that region lacks Cloud Scheduler support — publicly-reported tooling issues (GitHub `firebase/firebase-functions` #1293 and `firebase/firebase-tools` #6598 — **secondary, community-reported evidence, not an official product guarantee**) describe deployments to unsupported regions succeeding without a clear error, then failing at the IAM/scheduling layer [T18]. **Practical implication:** if `africa-south1` is chosen, scheduled/background functions (TRD22 §22.11 lists these as a Phase 1 deliverable — reminder-processing, subscription renewals, birthday campaigns per the Version 1 Engineering Blueprint §3.4) cannot rely on Firebase's automatic `onSchedule` helper as-is; they require either (a) an HTTPS-triggered (`onRequest`) function in `africa-south1` paired with a manually-provisioned Cloud Scheduler job in a supported region targeting it, or (b) placing scheduled functions in a Scheduler-supported region as part of a mixed-region design.
- **Cloud Tasks remains an unresolved architecture question for `africa-south1` — it is not solved by the same pattern as Cloud Scheduler unless that is independently confirmed.** No official documentation directly reviewed in this pass establishes that a Cloud Tasks queue in another region can securely and reliably invoke an `africa-south1` target with the same architectural cleanliness as Cloud Scheduler's HTTP-target model — Cloud Tasks queues, retry/dead-letter behavior, and payload handling are not identical to Cloud Scheduler's simpler cron-to-HTTP-endpoint design, and this pack does not claim they behave the same way under a cross-region setup. **If the Version 1 architecture requires a task-queue mechanism (as distinct from simple scheduled triggers), a queue in a supported region, an alternative queuing mechanism (e.g. Pub/Sub-based fan-out, confirmed available in `africa-south1` per §2), or a redesign must be evaluated separately before `africa-south1` can be treated as architecture-complete for that requirement.** See the added Cloud Tasks questions in the Remaining Technical Questions list (this pack's §9 and the Evidence-Gathering Report §14).

## 3. Firestore Location Consequences

- **Single-region** (e.g. `africa-south1`, `europe-west1` alone): lowest write latency for users near that region, lowest cost, but a **single-region outage affects the whole database** — no automatic multi-zone failover beyond Google's own intra-region redundancy.
- **Multi-region** (`eur3`, spanning `europe-west1`+`europe-west4` read-write and Finland as witness [T5]): higher availability guarantee (Google's published Firestore multi-region SLA is higher than single-region), at a **higher per-operation cost** and with **write latency that reflects the round-trip between the paired regions**, not just distance to the end user.
- **Durability:** Google's documented model treats multi-region as materially more durable against a regional-level incident; single-region relies on that region's own zone redundancy.
- **Compatibility with Functions/Storage:** Functions and Storage buckets are typically colocated with Firestore's region for lowest latency; a Firestore multi-region choice (`eur3`) does not have a matching Functions "multi-region" concept in the sources reviewed — Functions remain regional, so a multi-region Firestore choice still requires picking a specific region (or regions) for Functions, which is itself a mixed-region design decision.
- **Changing location later:** **Firestore's database location cannot be changed after creation without a full data migration** — this is treated as a well-established constraint of Firestore's architecture rather than independently re-confirmed against current documentation in this pass, and should be treated as a hard constraint: **the region choice, once a Firestore database is created, is effectively permanent for that database's lifetime.**

## 4. Latency

**No direct network-latency measurement tool was available to this research process.** The estimates below are inferred from (a) known regional internet-connectivity topology for Rwanda and Burundi and (b) third-party reference ping data between major cities — **these are estimates, not measurements, and are labeled as such throughout.**

- Rwanda and Burundi are both landlocked and reach the global internet via terrestrial fiber to coastal submarine-cable landing points, predominantly through **SEACOM and EASSy** (landing on the Indian Ocean coast) [T9]. Burundi specifically has no direct submarine landing and routes overland through Rwanda and Tanzania via multiple cross-border fiber links [T9]. A newer cable (Umoja) is reported to be improving direct connectivity from Rwanda/Uganda/Eastern DRC toward South Africa specifically, but was not confirmed as fully operational at the time of this research [T9].
- **Reference ping data** (WonderNetwork, a third-party latency-measurement service, for Johannesburg — not Kigali or Bujumbura, which were not available as measurement endpoints in the sources reviewed): Johannesburg↔London ≈ 160 ms, Johannesburg↔Amsterdam ≈ 165 ms, Johannesburg↔Frankfurt ≈ 170 ms [T10]. These figures describe *Johannesburg's* latency to Europe, not Kigali's or Bujumbura's latency to Johannesburg or to Europe directly — they are included only to characterize how well-connected `africa-south1` itself is to the European candidates, as a secondary data point.
- **Estimated latency for Kigali and Bujumbura to `africa-south1`:** likely **lower** than to any European candidate, given `africa-south1`'s status as "among the limited number of cities where successful [African] interconnection happens" [T9] and its direct SEACOM/EASSy-linked path — but no specific millisecond figure is available from the sources reviewed. **Labeled as: directional estimate only, not a measured or cited figure.**
- **Estimated latency for Kigali and Bujumbura to European candidates:** likely **higher** than to `africa-south1`, given the additional distance and the typical routing pattern (East Africa → submarine cable → often via the Middle East or around Africa → Europe) — again, **directional estimate only**.
- **Recommended next step before DEC-TECH-005 is finalized:** commission or obtain an actual synthetic latency test (e.g. a simple ping/traceroute from a Kigali- and Bujumbura-based vantage point, or a third-party network-measurement service with African vantage points) rather than relying on this pack's directional estimate for a final decision.

## 5. Pricing

**Assumptions stated separately from facts, per the required output format:**

- **Fact:** Google Cloud's network-egress pricing varies by *source region* and destination. Inter-region transfers between regions are priced from roughly **$0.05/GiB** (e.g. Europe↔North America) up to **$0.14/GiB** for transfers involving South America and Africa [T11]. Internet egress (Premium Tier) starts around **$0.12/GiB** to North America/Europe/Asia and **$0.19/GiB** to Australia/Indonesia/Korea; Standard Tier starts around **$0.085/GiB** for the first 10 TiB, declining at higher volumes [T11].
- **Fact:** Google publishes Firestore, Functions, and Storage pricing on a per-service basis; this research pass could not retrieve the complete, current per-region Firestore price table (the source page's content was too large to be returned by the fetch tool used) — **this is a stated tool limitation, not a finding that pricing is undifferentiated.** Google Cloud's documentation elsewhere groups regions into pricing tiers (e.g. the "Tier 1 / Tier 2" distinction already confirmed for Cloud Functions in §1/§2, where `africa-south1`, `europe-west1`, `europe-west4`, and `europe-west9` are Tier 1 while `europe-west3` is Tier 2 for Functions specifically [T3]) — a similar tiering likely applies to Firestore but was not independently confirmed for Firestore specifically in this pass.
- **Assumption (not fact):** given `africa-south1`'s status as a newer, smaller African region, it is reasonable to assume its egress and possibly compute pricing carries a premium relative to the large, mature European regions — this is an assumption based on Google's general regional-cost-tiering pattern, not a confirmed price comparison, and should be verified with Google's pricing calculator before being relied on.
- **No exact monthly cost is estimated in this pack**, per the explicit instruction not to fabricate a cost without stated usage assumptions — that exercise requires (a) a confirmed region, (b) confirmed pilot-scale usage projections (expected daily active users, writes/reads per user session, storage volume), neither of which exists yet at Phase 0/pre-Phase-1.

## 6. Reliability and Operations

- **Regional resilience:** all five single-region candidates share Google's standard intra-region zone redundancy; none has been reported with a distinctive incident history in the sources reviewed for this pass (a full Google Cloud Service Health history review was not completed — flagged as a follow-up, using `https://status.cloud.google.com/regional/africa` and the equivalent European dashboards) [T12].
- **`africa-south1` as the newest region (opened January 2024) [T2]** has a shorter operating track record than the European candidates (`europe-west1` in particular is one of Google's most mature regions) — this is a fact about operating history length, not a finding of lower reliability.
- **Future East African growth:** `africa-south1` is the only candidate with any Africa-continent proximity advantage for future expansion beyond Rwanda/Burundi (per §0's baseline, no specific future-expansion country's legal profile is presumed) — but its Cloud Scheduler gap (§2) is a concrete architectural limitation to weigh against that proximity advantage.
- **Migration difficulty:** per §3, a Firestore region choice is effectively permanent once the database is created — for **any** candidate, "wrong region" is a costly mistake to correct later (full data migration), which argues for resolving the latency-measurement and legal-confirmation gaps (§4, §0) before finalizing rather than after.

## 7. Architecture Compatibility

The Version 1 Engineering Blueprint's architecture (Firebase Authentication, Firestore, Cloud Functions, Cloud Storage, App Check, Cloud Messaging, scheduled Functions for reminders/renewals) does not, on the evidence gathered, cleanly fit a **single-region-everywhere** design if `africa-south1` is chosen alone, because of the confirmed Cloud Scheduler and Cloud Tasks gaps (§2). Three structural options, none selected here:

1. **Single-region European design** (e.g. `europe-west1`): every service checked in §2 is confirmed available in that one region for `europe-west1` specifically; no mixed-region complexity; higher latency from Kigali/Bujumbura than an African region would offer (directional estimate, §4). **Note:** "every service checked" reflects this pack's own §2 matrix, not an exhaustive audit of every GCP product — Cloud Run and Cloud Storage were independently re-confirmed for `europe-west1`, but several secondary services (Logging/Monitoring specifics) were not.
2. **`africa-south1` primary + a Scheduler-capable region for scheduled Functions**: lower latency for the primary Firestore/Functions/Storage workload, at the cost of a controlled mixed-region design (§2's manually-provisioned cross-region Scheduler pattern) and the added operational complexity of managing two regions. **This option addresses Cloud Scheduler specifically — it does not, by itself, resolve Cloud Tasks**, which remains a separate, unanswered architecture question (§2) requiring its own evaluation (a queue in a supported region, an alternative mechanism such as Pub/Sub, or a redesign) before this option can be called complete.
3. **`eur3` multi-region**: highest Firestore availability guarantee, at the cost of higher per-operation pricing (assumption, §5) and no equivalent multi-region option for Functions.

**Firebase Authentication's lack of a project-level location-selection control (§2) applies identically regardless of which of the three options above is chosen** — it is not a differentiator between candidates, only a fact to disclose to Part A's legal analysis, alongside the explicit limitation that Authentication's precise data-residency position requires direct provider confirmation and is not established by this pack.

## 9. Recommendation (Advisory Only — Not Final)

- **Preferred candidate (advisory):** `europe-west1` (Belgium) — of the candidates checked in §2, the one with the most complete confirmed service coverage (including both Cloud Scheduler and Cloud Tasks) combined with Tier 1 pricing and the longest operating track record, avoiding the mixed-region complexity `africa-south1` alone would require. **"Most complete confirmed coverage" reflects the specific service list checked in §2, not a claim that every possible GCP service was independently verified for this region.** This is a **conservative, lowest-operational-risk recommendation**, not a latency-optimized one.
- **Second-choice candidate (advisory):** `africa-south1` (Johannesburg) — likely the lowest-latency option for both Kigali and Bujumbura (directional estimate, not measured), and the most future-growth-aligned for East Africa, but requires resolving **two separate service gaps, not one**: Cloud Scheduler (a documented/strongly-supported cross-region HTTP-target pattern exists, §2) and Cloud Tasks (an unresolved architecture question with no equivalent confirmed pattern, §2) — or adopting a mixed-region design covering both — and carries an unconfirmed cost premium and a shorter operating track record.
- **Rejected from this shortlist, with reasons:** `europe-west3` (Tier 2 Functions pricing with no compensating advantage over `europe-west1`/`europe-west4`) and `europe-west9` (shares `africa-south1`'s Cloud Scheduler gap without `africa-south1`'s latency advantage). Both remain technically viable and are not excluded from future reconsideration — they are simply dominated by other candidates on the evidence gathered.
- **`eur3` multi-region** is not recommended as a first choice given its likely cost premium (assumption, §5) and the lack of an equivalent Functions multi-region concept, but remains worth revisiting if a stronger Firestore-availability guarantee becomes a priority.
- **Confidence level: low-to-moderate.** This recommendation is built on service-availability facts with high confidence, but on latency estimates and cost assumptions with low confidence (§4, §5), and on legal admissibility that is only "potentially" established (§0). It should be treated as a starting point for discussion, not a basis for immediate action.
- **Conditions that must be satisfied before confirmation:**
  1. Burundi's Ministerial adequacy list (contents, if issued) and its data protection Agency's operational status are confirmed (Part A §3/§7).
  2. Rwanda's Article 48/50 authorization pathway and realistic timeline are confirmed with NCSA or Rwandan counsel (Part A §7).
  3. An actual latency measurement (not an estimate) from Kigali and Bujumbura to `africa-south1` and to at least `europe-west1` is obtained.
  4. Firestore, Storage, and full pricing are independently confirmed per-candidate directly from Google's pricing calculator, not inferred from the Functions tiering pattern alone.
  5. If `africa-south1` is preferred over the conservative recommendation above, the Cloud Scheduler cross-region pattern (§2) is implemented and tested.
  6. **Cloud Tasks is separately and specifically resolved for `africa-south1`, if the Version 1 architecture requires a task-queue mechanism** — this is not covered by condition 5 above. Open questions requiring direct evaluation: (a) whether a Cloud Tasks queue in a supported region can securely and reliably invoke an `africa-south1` HTTPS target; (b) the authentication method for that cross-region call; (c) retry and dead-letter behavior under a cross-region configuration; (d) regional-failure behavior (what happens to queued tasks if either region degrades); (e) the latency and egress-cost implications of a cross-region queue; (f) data-residency implications for task payloads and metadata, given DEC-LEGAL-006's cross-border-transfer analysis (Part A). Until these are answered, `africa-south1` should not be treated as architecture-complete for any Phase 1 requirement that depends on Cloud Tasks specifically (as distinct from simple scheduled triggers, which Cloud Scheduler already addresses).
  7. Firebase Authentication's actual data-residency position is confirmed directly from Google's applicable service terms or data-processing documentation, or from the provider directly — this evidence pack's finding (§2) that Authentication lacks a location-selection control is not itself confirmation of where Authentication data resides.
