# Founder Preview — Local Runbook (EA-002)

**Purpose.** One reliable, local, deterministic 11thONUS Founder Preview: web app + Firebase emulators +
Functions + local PostgreSQL, loaded with a realistic seeded dataset, resettable to the same state.
**Local only.** Nothing here can reach a real project, a shared database or production.

> This is the foundation for Experience Assembly. It builds **no new screens**. Today it lets you sign in
> as every role and use the screens that already exist (onboarding, Business Dashboard, programmes, team,
> purchases, customer verification, rewards). Missing experiences are listed in
> [What the preview cannot show yet](#what-the-preview-cannot-show-yet).

## 1. Prerequisites (one time)

| Need                  | Notes                                                                                        |
| --------------------- | -------------------------------------------------------------------------------------------- |
| Node 20+ and pnpm 9   | `corepack enable` or `npm i -g pnpm`                                                         |
| Java 21+              | required by the Firestore emulator                                                           |
| Docker                | runs the local PostgreSQL (`docker-compose.postgres.yml`). No Docker? see _Own PostgreSQL_   |
| `pnpm install`        | from the repository root                                                                     |

## 2. Start (clean machine → working preview)

```bash
pnpm install
pnpm preview:start
```

`preview:start` is idempotent. It: starts PostgreSQL (Docker) → waits until healthy → **applies all
canonical migrations** → builds Functions → starts the Firebase emulators (Auth, Functions, Firestore,
UI) → loads reference data (Commerce Knowledge + the test-only Terms fixture) → **seeds the Founder
Preview dataset** (first run, or whenever the emulators were restarted and the data is inconsistent)
→ starts the web app → prints the URLs. First run takes roughly 1–2 minutes plus first-time emulator
downloads; a warm start takes about 15 seconds.

Open **http://localhost:5173** and sign in with Email/Password (accounts below).

| Command                | What it does                                                                               |
| ---------------------- | ------------------------------------------------------------------------------------------ |
| `pnpm preview:start`   | Bring everything up; keep existing seeded data if it is consistent                          |
| `pnpm preview:reset`   | **Guarded wipe → migrate → reseed.** Returns to the same deterministic state                |
| `pnpm preview:stop`    | Stop the web app and emulators. PostgreSQL is left running; data is never wiped by `stop`   |
| `pnpm preview:status`  | What is running, migration level, whether the seed is consistent                           |
| `pnpm preview:accounts`| Print every preview identity, plus each customer's Loyalty Number / QR reference           |
| `pnpm preview:verify`  | Compare live data to the committed expected fingerprint (proves determinism)              |
| `pnpm preview:migrate` | Apply canonical migrations to the local preview database only                              |
| `pnpm preview:seed`    | Seed a _clean_ preview (refuses if data exists — use `reset`)                              |

Ports: web **5173** · Auth **9099** · Functions **5001** · Firestore **8080** · Emulator UI **4000** ·
PostgreSQL **54329** (database `eleventhonus_platform_local`).

Logs and process ids live in `.preview/` (git-ignored). Emulator data is held in memory: stopping and
starting the emulators loses it, which is why `start` re-seeds automatically when it detects that.

## 3. Reset

```bash
pnpm preview:reset
pnpm preview:verify      # optional: proves the reset reproduced the exact expected state
```

Reset clears the Auth and Firestore emulators, drops and recreates the preview database schema, re-applies
migrations, reloads reference data and reseeds. IDs and timestamps are regenerated by the platform (they
differ every time); **everything logical is identical** — names, roles, Circle positions, Reward states,
Commercial balances, settlement states. That identity is what `preview:verify` asserts.

## 6. How the data is created

| Fact                                                                | Path                                                                                                                                    |
| ------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| Accounts, identities, Loyalty Numbers, QR identities                | Auth-emulator sign-up (as the web SDK does) + real `authenticate` callable                                                              |
| Businesses, Terms, submit-for-verification                          | Real `createBusiness`, `acceptBusinessTerms`, `submitBusinessForVerification` callables (Terms against the existing test-only fixture)  |
| Business activation                                                 | The real activation **command**, in-process (see §7)                                                                                    |
| Team                                                                | Real `createStaffInvitation` / `acceptStaffInvitation`; email verified via the emulator's real verification-code flow                   |
| Qualifying items, programmes, publication                           | Real `createQualifyingItem`, `createRewardProgram`, `publishRewardProgramVersion` callables                                           |
| Purchases, verification, dispute, redemption                        | Real `recordPurchase`, `verifyPurchase`, `raisePurchaseDispute`, `confirmRedemption` callables as the staff/manager/customer             |
| Operator record                                                     | The repository's own `bootstrapPlatformAdministrator` service                                                                           |
| Commercial accounts, trial, settlements, credit, restriction, debits| The real Commercial command services and consumption reconciliation, in-process (no endpoint exists yet — none is faked)               |

No database row is inserted directly. The seed reads IDs it needs from the platform's own read models.

## 7. Production-safety guards

* Every writing/destructive command first asserts: `PLATFORM_ENV=local`; project exactly `demo-11thonus`;
  Firestore and Auth emulator hosts are loopback; PostgreSQL host is loopback **and** the database is exactly
  `eleventhonus_platform_local` (the integration-test database `…_test` and any other name are refused);
  no Google credentials/Firebase token present; the Commercial admission gate is off. Otherwise it refuses and explains.
* The tooling forces those values onto every child process; a gate setting inherited from your shell is stripped.
* All fixtures live in `tests/preview/` — no production code imports them. No preview code exists in `apps/` or `functions/src/`.
* **Seed-only evidence.** Business activation and the Commercial commands require Platform-Administrator
  authority including verified two-factor evidence, and no Operator endpoint exists. The seed runs the same
  command in-process, supplying the second-factor evidence itself; the administrator-record check, Terms
  revalidation, idempotency and audit all still run. This is confined to `tests/preview/seed/adminServices.mjs`.
  Whether the Auth emulator can issue a genuine second-factor claim is unverified (EA-001 D-9).

## 8. Business Terms

Terms are **not bypassed**. The seed accepts Terms through the real `acceptBusinessTerms` callable against the
existing, Founder-authorised test-only fixture (`FD-PREVIEW-TERMS-001`, emulator only). The Business Terms
**screen** remains unavailable by design (`DEC-LEGAL-002` is open), so a Business you create *by hand* in the UI
can complete the establishment steps but cannot accept Terms or submit for verification from the screen.
Completing that live is a missing authorised seam, recorded for the Experience Assembly track — it is not
worked around here.

## 9. Playwright

```bash
pnpm preview:start          # keep running
pnpm test:e2e:preview       # real sign-in + real routes, desktop and phone viewport
```

Identities live in `tests/preview/identities.json` (import it from specs). Specs should reset to a known
state with `pnpm preview:reset` (or a future scenario variant) before journeys that mutate data.

## 10. Own PostgreSQL / troubleshooting

* **No Docker:** start any local PostgreSQL 16 with a database `eleventhonus_platform_local`, then
  `PREVIEW_POSTGRES_URL=postgres://user:pass@localhost:5432/eleventhonus_platform_local pnpm preview:start`.
  The URL must be loopback and name that exact database.
* **Corporate/sandbox proxy breaks the emulators** (symptom: _request blocked_ / emulator trigger registration
  fails): `PREVIEW_STRIP_PROXY=1 pnpm preview:start`.
* **Ports busy:** stop what uses 5173/9099/5001/8080/4000/54329, or `pnpm preview:stop` a previous run.
* **Something looks half-seeded:** `pnpm preview:reset`.
* **Emulators log:** `.preview/logs/emulators.log`; web log: `.preview/logs/web.log`.

## 11. What the preview cannot show yet

Frontline counter, redemption screen, Command Centre home, customer identity (Loyalty Number/QR), Circle
progress visual, Operator Console, Business-facing Commercial standing — none exist yet (Experience Assembly
packages). The data for all of them is already seeded and reachable through the real read models.

## 12. Requirements discovered for the later Cloudflare phone-access spike

(Recorded only; no tunnel is built here.)

* The web client **hard-codes** the emulator addresses (`127.0.0.1:9099` Auth, `127.0.0.1:5001` Functions —
  `apps/web/src/infrastructure/firebase/{auth,functions}.ts`); a phone cannot reach them. The origin must be made configurable
  or served same-origin through a proxy.
* The emulators bind to loopback by default (`firebase.json` sets no host) — good; they must stay private.
* Callables are plain HTTPS POSTs to `/<project>/<region>/<name>` with `{ "data": … }` — verified by the seed — so a
  path-allow-listing proxy is feasible; `connectFunctionsEmulator` is host+port only (custom-domain mode needed for HTTPS).
* Auth emulator **admin endpoints** (`/emulator/v1/…`: clear accounts, read verification codes) are used by the seed and
  must never be proxied.
* Vite dev blocks unknown `Host` headers; staff invitation links use `window.location.origin`, so they will carry the
  tunnel hostname.
* Email/Password sign-in works with no redirect; Google/Phone do not meaningfully work against the emulator remotely.
