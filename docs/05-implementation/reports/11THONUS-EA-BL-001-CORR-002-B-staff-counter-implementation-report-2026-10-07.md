## 4. Key behaviours and proofs
- **Retryable mapping (§14).** Found: a lost response/dropped connection reaches the SDK as `functions/internal`, which the shared mapping called non-retryable `failed` → the key holder would **discard the key**. `recordPurchase` now classifies `internal/unknown/cancelled` (and a bare network error) as uncertain/retryable; every other callable unchanged. Tests: unit, page-level, real-stack.
- **purchaseDate/idempotency (§13).** One intent = payload + `purchaseDate` + key; `resolvePurchaseDateInstant` is called only when an intent is prepared. Retry reuses all three; intentional edit, definitive failure or Serve next discards. Proven: page test with moving clock; **real-stack test** forwards the request to the server (commit) then drops the response, retries → identical payload/key/date, one new row; DB test: same key retry returns the original, changed date under the same key → `IDEMPOTENCY_CONFLICT`, revoked actor’s retry → `AUTH_FORBIDDEN` (authorisation still runs first; replay was **not** moved before it).
- **BR confidentiality (hard condition).** Staff `listRewardPrograms` lacks the key (server); the Counter additionally projects through a whitelist so the key is dropped even for Owner/Manager responses; not in DOM, query cache, request, errors, outcome; absence is never read (no client threshold logic). Staff cannot read the queue, approve, reject or verify (DB tests + `preview:counter-checks`).
- **Outcomes.** `waiting_for_customer`: “Purchase recorded. The customer needs to confirm it. Nothing has been earned yet.” `business_review_required`: “Purchase recorded. Business review is required before customer confirmation.” (success, `role=status`, no controls). Only routing/item/quantity retained from the server result.
- **Access.** Staff land on Counter; Owner/Manager shell unchanged (`counter` route reachable, no nav item added — nav-label test locks the list). Server authority unchanged; role only picks the shell; if the role cannot be read the page **fails closed** (error state, no shell) — never treated as Owner/Manager.

### 15.2 Existing progress architecture inspected (before any change)
- **Authoritative verified progress:** `loyalty_cycles.allocated_units` for the Customer's single current Cycle (`active` | `reward_available`; one per Customer/Program by partial unique index); threshold from the Cycle's locked version `required_verified_units`. Reward open ⇔ `rewards.state='available'` on that Cycle. Verified Units are minted only by the **Customer's** `verifyPurchase` (`admitPurchaseToLoyalty`).
- **Existing read models:** Owner/Manager `businessLoyaltyVisibilityRepository` (Business-wide lists, joins Loyalty Numbers — far too broad for Staff); Customer `customerExperienceRepository` / `customerExperienceProjection` (own cycles + `waiting_for_customer` units as a **separate** display value that never contributes to the Cycle).
- **Identity resolution:** `recordPurchase` resolves the presented Loyalty Number / QR in Firestore with purpose `merchant_transaction` (no routine audit event), then gates a Loyalty Number on the locked version's `sharedLoyaltyNumberAllowed` — the new read reuses exactly these.
- **§13 Product-Truth check (reward available + ordinary purchase):** `admitPurchaseToLoyalty` — when the current Cycle is `reward_available`, newly verified units get `pendingNow = quantity` and are **not allocated** until the Reward is redeemed. Recording an ordinary Purchase is therefore safe and consistent with Product Truth; **no conflict, no stop**. Slice B only informs Staff; it does not redeem.
- **Schema:** the read needs nothing new — every column/index it uses exists. **No migration, no new projection, no config.**

### 15.3 Limited-progress backend (`getCounterLoyaltyContext`)
Input (whitelisted at the transport boundary): `businessId`, `rewardProgramId`, and exactly ONE presented artifact (`loyaltyNumberValue` XOR `qrReference`) — **no Customer id in or out**. Server steps: (1) live `purchase.record` authority (the Counter's one authority — identical to `recordPurchase`/`listMyRecentCounterPurchases`; suspended/removed/non-members/Customers denied); (2) exactly-one-artifact shape; (3) the Programme must be an **active Programme of this Business** — decided *before any Customer is looked up* (unknown, foreign, paused or non-UUID ids are one neutral `programme_unavailable`); (4) artifact validation + the locked-version shared-number gate + the `merchant_transaction` lookup — **every** artifact failure (unknown, malformed, wrong QR, Loyalty Number on a QR-only Programme) is the SAME `customer_artifact_invalid_or_not_found` token; (5) three bounded, Business+Customer+Programme-anchored SELECTs. Read-only: it never opens or repairs a Cycle.
**Returned (4 values):** `verifiedUnits`, `requiredVerifiedUnits`, `rewardStatus` (`none`|`available`), `awaitingCustomerConfirmationUnits` (sum of the Customer's `waiting_for_customer` units in THIS Programme — same definition as the Customer's "Waiting for You").
**Explicitly excluded:** Customer id/name/phone/email/profile, Loyalty Number or QR echo, history, other Businesses/Programmes, Business-Review-held purchases (not counted — counting them would reveal routing), review fields, the review threshold, the Reward id/description, Cycle number.
**Enumeration:** a Staff member can already learn that a code is valid by recording against it; the read adds no new class of disclosure beyond four counts about the one Customer they are serving, and bad codes are indistinguishable. A per-actor rate limit does not exist anywhere in the repository; it is recorded as a follow-up candidate (see §15.12), not invented here.

### 15.4 Navigation architecture
Three **places** that are real routes (`NavLink`, `aria-current="page"`): **Counter** (`…/dashboard/counter`), **Activity** (`…/activity`), **Profile** (`…/profile`), plus one round **quick-action** button integrated in the bar (places vs actions). Unknown paths still fold to the Counter. The Counter is kept **mounted** (hidden) while Activity/Profile is open, so a transaction in progress is never lost and Browser Back walks the places normally; leaving the Counter closes the camera and stops loyalty reads. A new place starts at its top with its heading focused. The bar, app column and sheets are unchanged in width (`max-w-lg`, centred, mobile-only shell at every width).
**Counter view:** Identify customer → Loyalty status → Programme → Item → Quantity → Record purchase → Outcome / Serve next customer. The permanent Activity list and the embedded New-customer workflow are **removed** from it (Owner/Manager reaching `/counter` through their existing authority see the same transaction-focused column inside their unchanged dashboard shell; their Counter no longer carries the embedded list — their Purchases page is unchanged).

### 15.5 Loyalty-status UI and semantics
Shown **once the customer and the Programme are known — before recording**: `8 of 10 verified` / `2 more verified purchases until the 11th is on us`; near-reward emphasis at 1 to go; a **separate** line `1 purchase awaiting customer confirmation`; and, when `rewardStatus='available'`, a prominent amber **`11TH REWARD AVAILABLE — Let the customer know their reward is ready.`** alert above Record (no redemption control; "You can still record this purchase as usual"). The ordinal is `required + 1`, localised (11th / 11e). Never `10 of 10` because a purchase is pending; after Staff records, the outcome stays the truthful "Purchase recorded. The customer needs to confirm it. Nothing has been earned yet." and the verified count does not move until the Customer verifies. A failed/unavailable read is a quiet neutral note and never blocks recording. The browser keeps only the four whitelisted values (rebuilt field by field), under a short-lived cache entry partitioned by member, never retried, refreshed on return to the Counter.
