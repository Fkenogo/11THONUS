## 6. PostgreSQL driver/tooling selected and rationale

**Driver: `pg` (node-postgres), v8.13.1**, plus `@types/pg`. Rationale: mature (the de facto standard Postgres client for Node.js, used by virtually every non-ORM Node Postgres integration), minimal (a thin wire-protocol client with a built-in `Pool`, no schema/model layer imposed), and explicitly not an ORM — it exposes exactly the `pool.connect()` / `client.query()` / transaction primitives the approved design's explicit-repository, explicit-transaction-boundary architecture needs, with nothing else layered on top.

**Migration mechanism: hand-rolled, not a third-party migration library.** Rationale, explained per the task's required order: (1) inspected the existing dependency stack — no migration tool of any kind exists yet; (2) the requirement is narrow (ordered `.sql` files, a `schema_migrations` tracking table, checksum-verified idempotent re-run, optional `.down.sql` rollback) and does not need a general-purpose tool's surface area (templating, seed data, programmatic schema builders); (3) this keeps the total new dependency footprint at exactly one runtime package (`pg`) rather than two, while remaining fully mature/standard in its approach (the plain-SQL-file-plus-tracking-table pattern is the same design every popular Node migration tool — e.g. `node-pg-migrate`, `db-migrate` — uses internally); (4) it is explicitly not an ORM and introduces no schema-definition abstraction. See `functions/src/infrastructure/postgres/migrationRunner.ts` for the full implementation and its own rationale comment.

## 7. Datastore/transaction foundation

- `postgresConfig.ts` — environment-variable validation only (no I/O). Fail-closed: `PLATFORM_ENV` has no default at all; a `production` environment with no `PLATFORM_POSTGRES_URL` throws immediately. Local/test-only defaults point at the disposable Docker instance below and are never used in `production`.
- `postgresPool.ts` — wraps `pg.Pool` behind this repository's own type (`PlatformPostgresPool`), so no domain service will ever import `pg` directly; provides `closePostgresPool` for clean test/shutdown teardown.
- `postgresTransaction.ts` — `withPlatformTransaction(pool, fn)`: `BEGIN`/commit-or-rollback/`finally`-release, the single entry point every future Postgres-authoritative domain transaction must use. Proven by `postgresTransaction.postgres.test.ts` against a real Postgres instance (commit, rollback-on-throw with no partial write, connection cleanup/release, and concurrent-transaction read-committed isolation).

## 8. Migration foundation

`migrationRunner.ts` — `discoverMigrationFiles`, `getAppliedMigrations`, `migrateUp`, `migrateDown`. Its own `schema_migrations` bookkeeping table is the only table this bootstrap step creates directly (migration-system metadata intrinsic to the mechanism, not a numbered migration). Proven end-to-end against a real Postgres instance in `migrationRunner.postgres.test.ts` using a throwaway fixture migrations directory (never the package's real, shipped one): ordered execution, clean-empty-database bootstrap, current-version detection surviving a fresh connection pool, idempotent re-run with no destructive reset, and `.down.sql`-based rollback plus re-apply. Pure-filesystem discovery logic (ordering, naming-convention validation, duplicate-version detection, `.down.sql` pairing) is additionally covered by dependency-free unit tests in `migrationRunner.test.ts`.

## 18. Risks

- The migration runner's checksum-mismatch guard means an already-applied migration file must never be hand-edited after merge — a real but standard constraint of this pattern, documented in the module's own doc comment and enforced by a thrown error, not a silent skip.
- `pg.Pool`'s default sizing (`PLATFORM_POSTGRES_POOL_MAX=3`) is a documented starting point, not a load-tested production value — no production Cloud SQL instance exists yet to tune against, so this will need revisiting once one does.
- This package establishes readiness plumbing only; a `ready: true` result is not, and must never be read as, evidence that the 11thONUS Platform Operational Baseline itself has been reached (§8 of the design, restated in `platformFoundationReadiness.ts`'s own doc comment).

- No CI job currently runs `test:postgres` automatically (no CI configuration file was touched by this package, per its instruction not to modify unrelated files) — it must be run manually (or wired into CI by a follow-up, out-of-scope change) until then.
