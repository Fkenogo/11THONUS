## 5. Source-Authority Analysis

**Which document is authoritative?** TRD10 §10.5. Established by the Blueprint's own §0 text (quoted above), applied — not newly interpreted — per `ENG-P2-000A` §5's prior finding, independently re-verified here by direct read of Blueprint §0, TRD10 §10.5, and TRD8 §8.7.

**Why not assume TRD10 automatically overrides everything?** The Canonical Reference's own Document Hierarchy (§9) ranks the entire "Technical Requirements Document (Chapters 1–23)" as a single tier — it does not rank TRD chapters against each other, and does not by itself resolve a TRD8-vs-TRD10 disagreement. The resolvable question here is narrower and different: **Blueprint-vs-TRD10**, which the Blueprint's own text resolves explicitly and unconditionally in TRD10's favor, regardless of which TRD chapter the Blueprint's stale content originated from.

**Supporting evidence beyond the bare authority rule** (none of this invents new policy — all cited directly):
- TRD10 §10.2's **DAP-010** ("Archive, Do Not Erase") gives an explicit, reasoned architectural principle for `archivedAt`/`archivedBy` that TRD8 §8.7's bare `deletedAt`/`deletedBy` field list has no equivalent for.
- TRD10's `archivedAt`/`archivedBy` naming matches **PRD2 §7**'s own "Archived" customer-account-status value (verified directly: PRD2 §7 defines `Pending Verification`/`Active`/`Suspended`/`Locked`/`Closed`/`Archived` as the full status set, with "Archived" described as "Historical records retained. Account inactive.").
- TRD10 §10.2's **DAP-008** ("Server Time Is Authoritative") and **DAP-009** ("Version Every Evolving Contract") give reasoned grounding for the timestamp-generation and schema-version semantics respectively.
- TRD10 §10.2's **DAP-007** ("Country-Aware Data": "Country, currency, locale and timezone context shall be stored where they materially affect interpretation") grounds `countryCode`/`currencyCode`/`timezone`.

**Is the authority chain genuinely ambiguous, requiring a stop-and-report?** No. The Blueprint-vs-TRD10 question is unambiguous (the Blueprint's own rule). The narrower TRD8-vs-TRD10 divergence this task newly found is disclosed in §8 below rather than resolved, because resolving it is outside this task's scope, not because it is ambiguous — TRD10 remains the more specific, principle-grounded, on-topic source even there, but this task does not act on that observation beyond disclosing it.

## 6. Exact BaseMetadata Inconsistency

Four distinct, independently-verified differences between TRD10 §10.5 (authoritative) and the pre-correction Blueprint §3.3 / current `baseMetadata.ts`:

| # | Category | TRD10 §10.5 | Blueprint §3.3 (pre-correction) / current code |
|---|---|---|---|
| 1 | Field naming | `schemaVersion: number` | `version: number` |
| 2 | Optionality/nullability | `createdBy: string \| null`, `updatedBy: string \| null` — explicit, always-present-but-nullable | Untyped in the Blueprint text; non-nullable `string` in code |
| 3 | Field naming + semantics | `archivedAt?: Timestamp \| null`, `archivedBy?: string \| null` (archival, per DAP-010) | `deletedAt?: Timestamp`, `deletedBy?: string` (deletion framing) |
| 4 | Field presence | Scoped shape adds `currencyCode?`, `timezone?`; has no `languageCode` | Has `languageCode?`; lacks `currencyCode?`/`timezone?` |

None of these are purely cosmetic: #1 concerns what the version number *means* (schema/structural version vs. an unspecified generic counter); #2 concerns whether the type system permits `null` for system-initiated writes; #3 concerns a named architectural principle (data retention posture), not just a word choice; #4 concerns which fields actually exist on a document at all.

## 7. Corrected Normative Contract

The Blueprint's §3.3, now reading (verbatim, see the live document for the current version):

**Base fields (every authoritative Firestore document):**

| Field | Type | Required | Creation semantics | Update semantics | Mutability | Source of value | Nullability |
|---|---|---|---|---|---|---|---|
| `id` | `string` | Yes | Set once, at creation | Never changes | Immutable | Server (opaque, non-sequential, per TRD10 §10.2) | Not nullable |
| `schemaVersion` | `number` | Yes | Set at creation | Changed only when the document's structural shape changes (DAP-009) | Mutable (schema-change events only) | Server/schema-defining code | Not nullable |
| `status` | `string` | Yes | Set at creation | Changed on status transitions | Mutable | Server, per domain-specific status enum | Not nullable |
| `createdAt` | `Timestamp` | Yes | Set once, server-generated (DAP-008) | Never changes | Immutable | Server only — client-supplied timestamps prohibited | Not nullable |
| `createdBy` | `string \| null` | Yes (field always present) | Set once, at creation | Never changes | Immutable | Trusted server context; `null` for system-initiated writes | **Nullable** |
| `updatedAt` | `Timestamp` | Yes | Set at creation, equal to `createdAt` | Set on every subsequent write, server-generated (DAP-008) | Mutable | Server only | Not nullable |
| `updatedBy` | `string \| null` | Yes (field always present) | Set at creation | Set on every subsequent write | Mutable | Trusted server context; `null` for system-initiated writes | **Nullable** |

**Scoped fields (where applicable, per collection):**

| Field | Type | Required | Tenant/ownership scope | Notes |
|---|---|---|---|---|
| `businessId` | `string` | Optional (mandatory for business-owned records per DAP-006 once used) | Business | — |
| `customerId` | `string` | Optional | Customer | — |
| `countryCode` | `string` | Optional | Country | ISO 3166-1 alpha-2 (TRD10 §10.5's own "Required Standards") |
| `currencyCode` | `string` | Optional | Currency | ISO 4217 |
| `timezone` | `string` | Optional | Locale/regional | — |
| `archivedAt` | `Timestamp \| null` | Optional field, nullable value | — | Present-but-null while active; set once archived. Archival, never deletion (DAP-010). |
| `archivedBy` | `string \| null` | Optional field, nullable value | — | Same actor-attribution rule as `createdBy`/`updatedBy`. |

**`languageCode`:** not part of this shared contract. A real, mandatory field (PRD2 §6) on specific collections (`users`, `customerProfiles` — TRD10 §10.6.1–§10.6.2), not universal metadata.

**Timestamps:** server-generated only; client-supplied timestamps are prohibited (DAP-008), reinforced by DAP-003's "No Critical Client Writes."

**Creation/modification attribution:** represented by `createdBy`/`updatedBy`, nullable to permit system-initiated writes with no human actor, never by a client-supplied identity.

**Soft deletion/archival:** belongs in the scoped BaseMetadata shape as `archivedAt`/`archivedBy`, not as a separate contract, and not as "deletion."

**Version fields:** belong in the base BaseMetadata shape as `schemaVersion`, representing structural/schema version — this contract defines no separate optimistic-concurrency or record-revision mechanism; none is evidenced in TRD10.

**Cross-entity application:** base fields apply to every authoritative Firestore document; scoped fields apply "where applicable" per collection, consistent with TRD10 §10.5's own framing.

**Permitted exceptions:** none identified in any governing document.

**Validation expectations for implementation (`RES-005.2b`):** the corrected shape must be enforced by the TypeScript type definition and, per the task-brief's own TDD requirement, by a failing test written first for each changed field before the implementation changes.

## 9. Current Code Conformance Gap

**What the current code does:** `functions/src/shared/metadata/baseMetadata.ts` implements the pre-correction (Blueprint/TRD8) shape exactly: `version: number`; non-nullable `createdBy: string`/`updatedBy: string`; `deletedAt?: Timestamp`/`deletedBy?: string`; `languageCode?: string`; no `currencyCode`/`timezone`. Its own docstring cites "the Version 1 Engineering Blueprint §3.3" by name — it was built to conform to the document this task has just corrected, so it no longer conforms to the corrected document.

**How it differs from the corrected contract:** exactly the four differences in §6, now inverted (code has the old shape, corrected Blueprint has the new one).

**What `RES-005.2b` must change:**
1. Rename `version` → `schemaVersion` in the `BaseMetadata` type and every call site/consumer.
2. Change `createdBy`/`updatedBy` from `string` to `string | null`, and update any code that currently assumes non-null.
3. Rename `deletedAt`/`deletedBy` → `archivedAt`/`archivedBy`, confirming (during that task's own analysis) that no code currently relies on "deletion" semantics that would be broken by the archival framing.
4. Remove `languageCode` from the shared `BaseMetadata`/scoped type; add `currencyCode`/`timezone`; separately confirm whether `languageCode` needs adding to the `users`/`customerProfiles`-specific schemas (a distinct, not-yet-designed schema question, since those collection schemas do not yet exist in code).
5. Update `baseMetadata.test.ts` and any other test asserting the old field names/types.

**What must remain unchanged:** the overall `BaseMetadata` TypeScript type name and its consuming call pattern (`stampCreate`/`stampUpdate`, per the existing code structure) — the field-level differences in §6 are the only evidenced changes; no test, API, Firebase Rule, or unrelated data model may be touched by `RES-005.2b` beyond what conforms this one shared type to the corrected contract. None of this is implemented by this task.
