## 3. Objective

Every push and pull request against `main` is automatically checked (build, lint, format, typecheck, unit/component tests, and — where reliable in CI — Playwright and the Firebase Emulator Suite), and every future work package has a ready-to-copy pull-request template and implementation-report/change-log template to fill in.

## 4. Before Making Changes

The agent must confirm, and report explicitly before writing any file:

1. **ENG-P0-001 is Complete** — confirmed (see §1 above; do not re-verify from scratch, but do run `git log --oneline -3` and `git status --short` to confirm the local state matches before starting).
2. **What changed versus the original planning assumption:** the Engineering Implementation Programme's original "Expected Files/Areas" for ENG-P0-002 said `.github/` or equivalent CI config, `/docs/reports/` templates, `/docs/changes/` skeleton (TRD22 §22.39). The `/docs/changes/` file *already exists* (ENG-P0-001 created it, since TRD22 §22.39 requires the change log to start from the very first work package, not the second). This prompt does **not** ask the agent to create `docs/changes/IMPLEMENTATION_CHANGES.md` — only a reusable **template** for future entries, kept separate from the live log.
3. **Root script names and behavior are fixed by ENG-P0-001** (§2 above) — CI must call them exactly as they exist; it must not introduce parallel/duplicate script logic in the workflow YAML that could drift from `package.json`.
4. **Firestore Emulator requires a JRE.** GitHub Actions' standard `ubuntu-latest` runner image includes a Java runtime, but the agent must verify this explicitly (e.g. `java -version` as a workflow step, or an explicit `actions/setup-java` step if the default image's JRE proves insufficient) rather than assume it silently works — this was not something ENG-P0-001 needed to solve (only local `firebase emulators:exec` was required there), so it is new verification work for this prompt specifically.
5. **State the proposed CI workflow structure (jobs, triggers, caching key, artifact-on-failure plan) before writing the workflow YAML**, so scope is confirmed against §6/§7 below rather than discovered after the fact.

If any of the above reveals the repository is not in the state this prompt describes, **stop and report** rather than proceeding on an assumption (TRD22 §22.40).

## 5. Task

Add a GitHub Actions CI workflow that runs the existing validation scripts against every push and pull request targeting `main`; add a pull-request template; add an implementation-report template and a change-tracking entry template (both under `docs/`, distinct from the already-existing live `docs/changes/IMPLEMENTATION_CHANGES.md`); ensure Node/pnpm versions used in CI match the repository's pinned versions; cache pnpm dependencies; upload logs/artifacts on failure; verify the pipeline requires no secret to run.

## 6. In Scope

- One GitHub Actions workflow file (e.g. `.github/workflows/ci.yml`) triggered on `push` to `main`, on `pull_request` targeting `main`, and on `workflow_dispatch` (a controlled manual rerun path requiring no secret). The feature-branch pull request remains the preferred validation route; `workflow_dispatch` is a convenience, not a substitute for it.
- Workflow steps, in order, each a separate job step (not concatenated into one opaque script) so individual failures are attributable:
  1. Checkout.
  2. Set up Node (version matching root `package.json`'s `engines.node`, e.g. `20.x`) and pnpm (version matching the pinned `packageManager` field, `pnpm@9.15.9`) — use `pnpm/action-setup` with an explicit version rather than relying on Corepack auto-activation (ENG-P0-001 hit a local Corepack/Node bug on this machine; GitHub-hosted runners are a different environment and may not reproduce it, but pinning the version explicitly via the action avoids the question entirely rather than gambling on it).
  3. Restore/save a pnpm store cache keyed on the hash of `pnpm-lock.yaml`.
  4. `pnpm install --frozen-lockfile`.
  5. `pnpm build`.
  6. `pnpm lint`.
  7. `pnpm format:check`.
  8. `pnpm typecheck`.
  9. `pnpm test`.
  10. Install Playwright's Chromium browser (`pnpm exec playwright install --with-deps chromium`), then `pnpm test:e2e`.
  11. Firebase Emulator Suite validation, only if it can be made to run reliably in CI within a reasonable time budget (verify the Firestore emulator's JRE dependency per §4.4 first) — `pnpm emulators:validate`. If, after genuine investigation, this step cannot be made reliable in CI (e.g. a real, documented flakiness or startup-time problem specific to the CI runner, not a shortcut to avoid the work), the agent documents exactly why in the Implementation Report and either omits the step with that justification or marks it `continue-on-error` with a clear comment — it does not silently drop it without explanation.
- On any step failure: upload `playwright-report/`, `test-results/`, and (if the emulator step ran) `firebase-debug.log`/`firestore-debug.log` as workflow artifacts, so failures are debuggable from the Actions UI without local reproduction.
- `.github/PULL_REQUEST_TEMPLATE.md` — sections for: summary, related work package/requirement/decision IDs, testing performed, screenshots (where applicable), rollback plan, checklist (build/lint/format/typecheck/tests green locally, no unrelated files, changes-tracking file updated).
- An implementation-report **template** (e.g. `docs/05-implementation/reports/TEMPLATE.md`), structured to match the [Implementation Prompt Standard](../../06-engineering-governance/implementation-prompt-standard.md) §3's exact reporting list (files modified; diff summary; commands executed; tests and results; dependencies added; configuration changes; migrations; risks; rollback instructions; unresolved issues) — a fill-in-the-blanks skeleton, not prose.
- A change-tracking **entry template** (e.g. a `## Template` section appended to the top of `docs/changes/IMPLEMENTATION_CHANGES.md` itself, clearly marked as a template and not a real entry, or a separate `docs/changes/ENTRY_TEMPLATE.md` — the agent's choice, stated and justified in the Implementation Report) matching the field list TRD22 §22.39 already specifies (date, phase, task, status, files changed, tests, configuration, migrations, risks, rollback, report link) and the pattern already used by ENG-P0-001's existing entries in that file.
- Verifying and stating explicitly in the Implementation Report that the entire pipeline requires **zero** GitHub Actions secrets (no Firebase service account, no API token) — the emulator suite's `demo-11thonus` project needs none, and nothing else in the pipeline talks to any external service.

## 7. Out of Scope

- Firebase deployment of any kind, from CI or otherwise.
- Any live Firebase project access, project creation, or credential/secret configuration.
- Selecting a Firebase region (DEC-TECH-005 remains open).
- Selecting any provider (error monitoring, payment, SMS, email — all remain open decisions).
- Any product-domain implementation (Identity, Purchase, Loyalty, Reward, or any other domain).
- Any application feature work of any kind.
- Modifying `apps/web` or `functions` source code, tests, or dependencies — CI wraps the existing scripts, it does not change what they do.
- Modifying `package.json`, `pnpm-workspace.yaml`, `pnpm-lock.yaml`, `eslint.config.js`, `.prettierrc`, `firebase.json`, or any other file ENG-P0-001 already produced, except where a workflow step genuinely requires a new, narrowly-scoped root script alias (state and justify any such addition explicitly; prefer calling existing scripts as-is).
- Documentation changes outside this work package's own templates and its own change-tracking/prompt-register entries (no PRD/TRD/Constitution/standards edits).
- Branch protection rule configuration in the GitHub repository settings (that is a GitHub-side administrative action for the Founder, not a file this agent can create).

## 8. Constraints

- Maintain the current architecture and tooling exactly as ENG-P0-001 established it (§2/§4 above) — do not rename, restructure, or "improve" existing scripts or config as a side effect of adding CI.
- Do not modify unrelated files.
- Do not bypass domain services (none exist yet).
- No direct authoritative client writes (not applicable — infrastructure only).
- Preserve localization and security boundaries (not yet applicable — no product code exists).
- Avoid speculative refactoring.
- The CI pipeline must be genuinely **secret-free** — if any step appears to require a secret, stop and report rather than adding one (TRD22 §22.40 — "a required provider contract is unavailable").
- Per TRD22 §22.10's exit criteria ("CI passes"), this work package's own successful CI run against its own PR is required evidence, not merely local script success.

## 9. Acceptance Criteria

- A GitHub Actions workflow runs automatically on push/PR to `main` and executes build, lint, format:check, typecheck, and unit/component tests, all passing.
- Playwright e2e runs in CI and passes (or, if genuinely infeasible, is documented per §6's investigation requirement — not silently omitted).
- Firebase Emulator Suite validation runs in CI and passes, or is documented per §6's investigation requirement if genuinely infeasible.
- Node and pnpm versions used in CI match the repository's pinned versions exactly (root `engines.node`, `packageManager`).
- pnpm dependencies are cached between runs.
- On failure, relevant logs/artifacts are uploaded and retrievable from the Actions UI.
- The pipeline requires zero secrets.
- `.github/PULL_REQUEST_TEMPLATE.md` exists and covers the fields in §6.
- An implementation-report template and a change-tracking entry template both exist, matching TRD22 §22.39 / the Implementation Prompt Standard §3.
- No product-domain application source code, schema, service, route, component or test is introduced by ENG-P0-002. (The governed documentation tree, `docs/`, may legitimately contain product-domain documentation — that is unrelated to this criterion, which governs only what this work package itself introduces.)

## 10. Required Tests / Validation

- The workflow itself, triggered by this work package's own PR (or a manually-dispatched run if PRs are not yet the operating model), is the primary validation — a CI config is not "tested" by local script success alone.
- Local dry-run of every script the workflow calls (`pnpm install --frozen-lockfile`, `pnpm build`, `pnpm lint`, `pnpm format:check`, `pnpm typecheck`, `pnpm test`, `pnpm test:e2e`, `pnpm emulators:validate`) to confirm they still pass unmodified before wiring them into CI.
- Confirm the workflow YAML is valid (e.g. `actionlint` if available, or GitHub's own workflow validation on push).

## 12. Reporting Requirements

Per the [Implementation Prompt Standard](../../06-engineering-governance/implementation-prompt-standard.md) §3, the agent's Implementation Report must include: files created; files modified; command/diff summary; commands executed; tests and results (including the actual CI run's outcome, linked); dependencies added (none expected — CI actions are not npm dependencies, but note any GitHub Action versions pinned); configuration changes; migrations (none expected); risks; unresolved issues (explicitly including whether the Emulator Suite step was reliable in CI or required the documented fallback per §6); the markdown implementation report itself; and the update to `docs/changes/IMPLEMENTATION_CHANGES.md` using the new template this work package creates.

**Rollback instructions must enumerate and reverse every file this work package actually creates or modifies** — not a shorthand summary. At minimum, the rollback section names each of the following individually, as applicable to what was actually built:

- the GitHub Actions workflow file (e.g. `.github/workflows/ci.yml`);
- `.github/PULL_REQUEST_TEMPLATE.md`;
- the implementation-report template (e.g. `docs/05-implementation/reports/TEMPLATE.md`);
- the change-entry template (e.g. `docs/changes/ENTRY_TEMPLATE.md`, or the template section if appended within `docs/changes/IMPLEMENTATION_CHANGES.md` itself);
- this work package's own Implementation Report file;
- this work package's own entry appended to `docs/changes/IMPLEMENTATION_CHANGES.md`;
- any status/row changes made to the Coding-Agent Prompt Register and/or the Engineering Implementation Programme to record ENG-P0-002's own progression (Ready → In Progress → ... → Complete).

A rollback description that only says "remove the workflow and templates" is incomplete and must not be accepted at Technical Review.
